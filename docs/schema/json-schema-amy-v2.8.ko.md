Read The Room: Vancouver Life - 시스템 디자인 가이드 (v2.7)
1. 목적
이 문서는 Read The Room의 시스템 디자인 문서를 실제 데이터 구조로 옮기기 위한 구현 기준이다.  
 목적: Read The Room의 시스템 디자인 문서를 데이터 구조로 구현하기 위한 기준.
 캐릭터: 모든 텍스트는 주인공 에이미(Amy)의 시점과 이름을 명시하여 몰입감을 극대화한다.
 
2. 스키마 상태
구조 최적화: 로컬 DB 관리 편의를 위해 불필요한 최상위 메타데이터(version, character 등)와 중복 계층(situation 객체)을 삭제한 평면적 구조를 채택한다.
타입 기반 제어: 기존 isPhaseEnd, isEnding 플래그를 type 필드로 통합하여 엔진 로직을 단순화한다.
ID 정렬: 메인 흐름과 예외 상황, 요약 노드를 ID 범위로 격리하여 관리 효율을 높인다.

3. 최상위 구조 (Root)
최상위 배열이나 복잡한 객체 대신, Day를 키(Key)로 하는 객체 구조를 권장한다. 파일명이 scenarios_ken.json이므로 내부의 중복된 캐릭터 정보는 생략한다.

3. 최상위 구조

  "Day1": {
    "1": { "id": 1, "type": "NORMAL", ... },
    "2": { "id": 2, "type": "NORMAL", ... }
  },
  "Day2": {
    "10": { "id": 10, "type": "NORMAL", ... }
  }
}

4. 노드 타입 및 ID 범위 준수 (Range Management)
번호만으로 데이터의 성격을 즉시 파악할 수 있도록 범위를 고정한다.

1 ~ 999: 메인 시나리오 (NORMAL)  

1000 ~ 1999: 하루/페이즈 요약 (SUMMARY)

9000 ~ 9999: 예외 분기 구간 (NORMAL)  

9999 이상: 최종 결말 (ENDING)

5. node 타입 규칙
기존의 Boolean 플래그를 대체하는 핵심 필드이다.

NORMAL: 일반적인 스토리 진행 및 선택지가 존재하는 노드.  

SUMMARY: (구 isPhaseEnd) 하루가 종료될 때 나타나는 회고 및 지식 요약 노드.

ENDING: (구 isEnding) 게임 전체의 이야기가 마무리되는 최종 노드.

6. 노드(Node) 상세 구조 (v2.7 다이어트 버전)
situation 객체를 해체하여 필드를 최상위로 노출하고 가독성을 높였다.

8. choices: 선택지 구성 및 비중 규칙
모든 노드는 기본적으로 3개의 선택지를 포함하며, 아래의 배분 규칙을 엄격히 준수합니다.
1) 기본 선택지 (Core Pool)
대부분의 노드는 아래 3가지 타입 중 상황에 가장 적합한 조합으로 구성합니다
GROWTH: 정석적인 성장, 영어 실력 및 통찰력 위주.
STABLE: 감정적 안정, 관계 유지 및 체력 보존.
REALIST: 경제적 이득, 현실적인 효율성 강조.
2) 히든 선택지 (Hidden Pool) 
- 비중 제한히든 피스는 전체 노드의 20% 내외로만 배치하여 희소성을 유지합니다. 
히든 피스가 포함되는 노드는 [기본 2개 + 히든 1개]의 구성을 가집니다.
타입 (Type)성격 및 역할등장 빈도
HIDDEN_JOKER엉뚱함, 치트키. 예측 불가능한 스탯 변화와 유머.10문항 당 1개
HIDDEN_ESCAPE모면. 꼼수로 위기를 넘기지만 추후 대가가 따름.10문항 당 1개

수하물 분실 대기 (ID 3 - STABLE):

기존: "켄은 멍하니 벨트만 봅니다."

수정: "★ 저런... 켄은 멈춰버린 벨트 앞에서 할 말을 잃었습니다. 낯선 땅에서의 첫날이 이토록 가혹할 줄은 몰랐네요."  

취조실 고립 (ID 9001 - REALIST):

기존: "켄의 멘탈은 너덜너덜하지만..."

수정: "★ 뼈아픈... 3시간의 취조 끝에 겨우 풀려났지만, 켄의 자존감은 이미 바닥에 떨어졌습니다. 밴쿠버는 생각보다 훨씬 차갑습니다."  

마트 결제 거부 (ID 9004 - REALIST):

기존: "켄은 민망함을 무릅쓰고..."

수정: "★ 아차... 물건을 덜어내는 켄의 손등 위로 사람들의 따가운 시선이 꽂힙니다. 이 5분이 켄에게는 5시간처럼 느껴집니다."

feedback 필드 (심리적 매운맛)
선택 직후 켄이 느끼는 당혹감, 수치심, 혹은 사회의 냉정함을 묘사하기 가장 좋습니다.

정의 방법: 단순히 "실패했다"가 아니라, 주변의 시선이나 켄의 내적 갈등을 묘사합니다.

예시: "feedback": { "ko": "★ 대박! 켄은 호의인 줄 알았지만, 밴쿠버의 친절에는 영수증이 따른다는 것을 뼈아프게 깨닫습니다. 주변의 차가운 시선은 덤입니다.", "en": "★ Epic Fail! Ken thought it was kindness, but he painfully learns that Vancouver's favors come with a bill. The cold stares from others are a bonus." }
statChanges: 6개 핵심 스탯(relation 포함)을 모두 반영한다.
statChanges의 불균형 (수치적 매운맛)
현실은 노력(Growth)한다고 항상 보상이 따르지 않으며, 실수의 대가가 가혹하다는 것을 숫자로 보여줍니다.

정의 방법: 특정 선택지에서 스탯을 파격적으로 깎거나, 얻는 것보다 잃는 것이 많은 상황을 만듭니다. 특히 funds와 mental 스탯을 활용하세요.

예시: 실수 한 번에 funds: -150 (바가지), mental: -50 (자괴감) 처럼 하이 리스크-로우 리턴 구조를 설계합니다.
10. 흐름 및 예외 규칙
복귀: 9000번대 분기(민망함, 실수 등 체험) 후에는 반드시 메인 흐름으로 복귀한다.  
시스템 디자인 가이드(v2.1)와 v2.7 스키마 규칙을 바탕으로 분석했을 때, '현실의 매운맛'을 정의하고 삽입하기 가장 좋은 위치는 크게 세 곳입니다.
9000번대도 보기는 3개로 하고 정석적인 해결책, 문화의 차이를 알려주는 헷갈리는 답안, 유머나 잘못된 선택에 따라 강력한 패널티나 게임 아웃되거나,
적절한 해결책으로 위기를 모면/ 분위기를 쇄신한다.

3. 작성 가이드라인 업데이트
감정의 일치: 기쁜 성취(성공적 주문, 카드 개통 등)에는 "★ 대박!" 혹은 "★ 성공!"을 사용하십시오.  

부정적 결과의 세분화: 금전적 손해는 "★ 뼈아픈", 심리적 위축은 "★ 저런" 혹은 "★ 울컥"으로 나누어 작성하면 유저가 켄의 입장에 더 깊이 동감할 수 있습니다.  

시점 유지: 모든 문구는 제3자의 객관적 서술보다는 켄의 곁에서 그를 지켜보는 듯한 나레이션 톤을 유지하는 것이 좋습니다.

잘못된 판단을 했을 때 바로 다음 에피소드로 가는 것이 아니라, '고생하는 과정'을 강제로 체험하게 합니다.

정의 방법: 입국 심사에서 말을 더듬었을 때 바로 통과되는 게 아니라, 9001번(정밀 검사실) 노드로 보내서 한참을 고생한 뒤에야 메인 스토리로 복귀하게 만듭니다.

역할: 플레이어에게 "판단 한 번에 내 시간이 낭비될 수 있다"는 현실적인 압박감을 줍니다.

💡 전문가의 제안: tip 필드의 재해석
가이드 7번에서 tip은 "현지에서는 ~하게 작동한다"는 정보성 문장으로 쓰라고 정의되어 있습니다. 이를 '매운맛 경고'로 활용해 보세요.

기존: "캐나다에서는 팁을 15% 이상 낸다."

매운맛 버전: "캐나다에서 팁을 아끼려다간 서버의 노골적인 무시와 마주칠 수 있습니다. 당신의 멘탈 수치를 지키려면 지갑을 여는 게 현명할지도 모릅니다."


종료: 엔진은 type: "SUMMARY"를 감지하면 하루를 정리하고, type: "ENDING"을 감지하면 최종 종료 처리한다.
